# Bundled ShellHub Remote Access

Soul Room starts a pinned ShellHub Community Edition deployment with the normal
Compose stack. ShellHub remains a separate security boundary for SSH transport,
keys, firewall rules, users, and device acceptance; Soul Room owns fleet RBAC,
device mapping, and the audit event that precedes a remote-access launch.

Managed devices do not expose port 22. The ShellHub agent creates an outbound
secure WebSocket to the bundled gateway.

## Local Endpoints

| Purpose | Default |
| --- | --- |
| ShellHub setup and web portal | `http://localhost:8088` |
| ShellHub SSH gateway | `localhost:22222` |
| Soul Room remote-access URL | Preconfigured as `http://localhost:8088` |

The deployment pins ShellHub `v0.26.0`. Its signing keys are generated on first
startup into the private `shellhub-keys` Docker volume. They are never stored in
Git or `.env`. ShellHub records are stored in its dedicated
`shellhub-postgres-data` volume.

## First Startup

Start the complete platform from `cloud-infra`:

```bash
docker compose up --build -d
```

Open `http://localhost:8088/setup`, create the ShellHub administrator, and
create the first namespace. This intentional one-time setup avoids shipping a
known ShellHub password. Record the namespace tenant ID.

For a physical device, configure the host address before starting Compose:

```dotenv
SOULROOM_SHELLHUB_DOMAIN=localhost
SOULROOM_SHELLHUB_URL=http://192.168.1.20:8088
SOULROOM_SHELLHUB_HTTP_PORT=8088
SOULROOM_SHELLHUB_SSH_PORT=22222
SOULROOM_SHELLHUB_POSTGRES_PASSWORD=replace-with-a-long-unique-password
```

`SOULROOM_SHELLHUB_DOMAIN` must be a hostname, not a raw IP address. Keep
`localhost` for an IP-only development setup. In production, set it to the real
ShellHub DNS name used by devices and operators.

## Install The Device Agent

ShellHub and Soul Room use separate device agents. Keep `edge-agent` for fleet
operations and install `shellhub-agent` only on devices where interactive
maintenance is permitted.

For Ubuntu with Docker or Podman, use the installation command generated by
the ShellHub **Add device** page. It contains the local server address and the
namespace tenant ID. Review scripts before running them as root.

For an embedded image without a container runtime, build the native ShellHub
agent or add the official `meta-shellhub` Yocto layer. Configure:

```text
SHELLHUB_SERVER_ADDRESS=http://192.168.1.20:8088
SHELLHUB_TENANT_ID=<namespace-tenant-id>
```

After the agent connects, accept the pending device in ShellHub. Copy its SSHID,
which has a form similar to:

```text
namespace.device@192.168.1.20
```

In Soul Room, open **Remote access**, select the corresponding fleet device,
and save that SSHID. Select the existing Linux user before opening the portal or
copying the SSH command. With the default local port, the generated command is:

```bash
ssh -p 22222 linux-user@namespace.device@192.168.1.20
```

Use public-key authentication and ShellHub firewall rules. Soul Room does not
store Linux passwords or reusable SSH private keys.

## Persistence And Reset

Normal rebuilds retain ShellHub keys, administrator, namespaces, and devices.
To stop without deleting data:

```bash
docker compose down
```

To intentionally erase the complete local installation, including ShellHub:

```bash
docker compose down -v
```

The reset is destructive. Back up customer installations before removing
volumes.

## Production Boundary

The bundled defaults use HTTP for local development. Do not expose them directly
to the internet. A hosted deployment must use dedicated DNS names, trusted TLS,
WebSocket-aware reverse proxying, generated database secrets, restricted
firewalls, monitored backups, and a tested upgrade process. Community Edition
does not include every advanced authentication, recording, auditing, or HA
feature available in ShellHub Enterprise; verify the required edition before
promising those features to customers.
